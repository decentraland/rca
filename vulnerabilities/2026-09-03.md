# September 3, 2026 - The Auth request page simulated a typed-data field that was not the one being signed

|                          |                   |
| -----------------------: | :---------------- |
|             **Reported** | September-03-2026 |
|           **Mitigation** | September-11-2026 |
|   **Solution Completed** | September-11-2026 |

## Description

- Third case in the same family as [2026-08-27](2026-08-27.md) and
  [2026-09-02](2026-09-02-2.md): the payload the request page reviews and the payload the wallet
  signs are built separately. The September 2 fix required signature requests to arrive in a
  canonical shape — `[signer address, exactly one typed JSON payload]`. This case uses exactly that
  shape, passes the new guard, and diverges **inside** the single typed-data object instead.
- For a `MetaTransaction` payload, `decodeMetaTransactionTypedData` checked `primaryType` and then
  read `message.functionSignature` to build the simulation. It never looked at
  `types.MetaTransaction` to confirm that field was part of the declared struct.
- Marketplace V4 declares and hashes a different field: its type is
  `MetaTransaction(uint256 nonce, address from, bytes functionData)` and it executes `functionData`.
  Typed data only covers the fields its type declares, so adding an undeclared `functionSignature`
  to the message does not change the hash the wallet signs.
- One request therefore carried two calls. `functionData` held `accept(...)` on a Marketplace trade
  that pulled the victim's token balance to the attacker; `functionSignature` held a read-only
  `getNonce(victim)`. The page simulated the read-only call and reported a successful result with no
  asset movement. No risk acknowledgement was required, because the simulation succeeded and
  `MetaTransaction` is not one of the payload types classified as high risk. **Allow** produced a
  valid signature over the trade, which anyone could then relay.
- The optional raw-data view did not restore informed consent. It shows the single typed-data
  object, in which the malicious call is opaque ABI-encoded hex the page does not decode, with
  nothing indicating that the field used for the preview sits outside the signed struct.
- Preconditions were the same as the rest of the family: the attacker hosts the request page, the
  victim opens it and approves within the request's 300-second lifetime, and only email and social
  wallets are exposed, since browser wallets show the real payload in their own confirmation. The
  path is not reachable from the official client.

### Root cause

The field the page read for its preview was chosen by name, not by the schema the signature covers.
`primaryType` was validated and the fields under it were not, so a message could carry an
execution-like field the signature did not include, and the page would review it as if it were the
transaction. Constraining the shape of the request, which the September 2 fix did, says nothing
about what is inside the one payload that shape allows.

## Severity

Websites & Applications - Critical.

Same calibration as the rest of the family. It matched "performing malicious interactions with an
already-connected wallet such as modifying transaction arguments or parameters ... stealing funds
or assets", and sat at the lower end of the tier because the decisive step happens on a page the
attacker hosts, the victim has to approve it, and only email and social wallets are affected. Loss
is bounded by the victim's token balance and the allowance the Marketplace already held.

## Solution

Fixed in [Auth 5.2.0](https://github.com/decentraland/auth/releases/tag/5.2.0) (September 11):

- **Bind the preview to the signed schema (root cause).** A `MetaTransaction` whose message carries
  any field outside its declared struct, or whose calldata field is not the one the contract hashes,
  is refused before anything is rendered. The bytes simulated and presented are the bytes included
  in the hash and later executed.
- **Fail visibly instead of reassuringly.** Anything the page cannot fully account for is now shown
  as its raw payload behind a mandatory risk acknowledgement, rather than as a clean summary derived
  from a field nobody verified.
