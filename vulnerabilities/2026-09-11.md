# September 11, 2026 - A World restricted to a community let non-members in

|                          |                   |
| -----------------------: | :---------------- |
|             **Reported** | September-11-2026 |
|           **Mitigation** | September-15-2026 |
|   **Solution Completed** | September-15-2026 |

## Description

- A World owner can gate access with a wallet list, with one or more communities, or both.
  `checkAllowList` in worlds-content-server tries the wallet list first and, failing that, calls the
  Social Service at `POST /v1/members/:address/communities` with the World's community ids, granting
  access when the response carries at least one item.
- The query behind that endpoint did not require membership. `getVisibleCommunitiesByIds` returns a
  community when it is active, the wallet is not banned, and **either** a membership row exists
  **or** the community is listed. Its own integration tests expected listed communities, public and
  private alike, to be returned for a non-member.
- So for any World gated on a listed community, any signed wallet passed the check.
  `/worlds/:worldName/comms` then issued the five-minute room credential — join, subscribe, publish
  microphone, publish data — and the outsider entered under their own identity, able to hear
  participants, read room data, see who else was present, and speak or send data into the room.
- The affected population was real rather than theoretical: a World deployed the day before was
  gated on a private community with 73 members, and a signed listing request from an unrelated
  wallet returned that community with no role.
- Wallet lists and unlisted communities were unaffected. World capacity, platform bans and World
  bans still applied, and removing the community from the World's permissions or changing the access
  mode stopped new credentials immediately.

### Root cause

The caller asked a question the endpoint did not answer. Its name and its call site read as "which
of these communities is this wallet a member of", while the query behind it answered "which of these
communities may this wallet see", and visibility is satisfied by the community simply being listed.
Authorization was taken from a non-empty result, so the two meanings never had to agree.

## Severity

Websites & Applications - High.

A signed outsider entered a room a World owner had deliberately restricted, with full participation
rights and no interaction from anyone inside. Kept below Critical because what the credential grants
is presence in that room — the public wallet addresses of the other participants, room data messages
and voice — and no confidential user information; it lasts five minutes, World and platform bans
still apply, and the owner can close the path immediately by changing the access mode.

## Solution

[Return only memberships from the batch member communities endpoint](https://github.com/decentraland/social-service-ea/pull/498)
(merged September 15):

- **Require a membership row (root cause).** The batch query now inner-joins `community_members`, so
  a listed community is no longer returned for a wallet that does not belong to it.
- **Make the name match the answer.** The method was renamed to `getMemberCommunitiesByIds` and
  returns the wallet's role alongside each community, keeping "may this wallet see or join this
  community" separate from "is this wallet a member of it".
