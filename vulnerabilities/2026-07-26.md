# July 26, 2026 - Client-supplied `asset_pack_id` lets any user insert assets into another user's Builder asset pack

|                          |               |
| -----------------------: | :------------ |
| **Reported on Immunefi** | July-26-2026  |
|           **Mitigation** | July-29-2026  |
|   **Solution Completed** | July-29-2026  |

## Description

- `PUT /v1/assetPacks/:id` authorized the parent row and wrote its children verbatim. `upsertAssetPack` (`builder-server/src/AssetPack/AssetPack.router.ts`) checked `new Ownable(AssetPack).canUpsert(id, eth_address)`, rejected a body whose `assetPack.id` disagreed with the URL, and force-overwrote the pack's own `eth_address` from the session — then wrote each nested asset as supplied: `assets.map((asset) => new Asset(asset).upsert())`. Every asset carries its own `asset_pack_id`, a required client-supplied field in `assetSchema` (`src/Asset/Asset.types.ts`), which the handler never compared to the URL `id` and never rewrote; the string did not appear anywhere in the router. The parent was authorized, the children pointed wherever the request said.
- The two guards that look like they cover this are keyed on the **asset** id, not the pack: `Asset.existsAnyWithADifferentEthAddress(assetIds, eth_address)` and `Asset.existsAnyWithADifferentAssetPackId(assetIds, id)`. A freshly generated asset UUID matches zero existing rows, so neither fires. They stop an *existing* asset being re-pointed, and say nothing about a *new* asset declaring someone else's `asset_pack_id`.
- Demonstrated against production on July 26, 2026 with two self-generated identities. The attacker `PUT`s its **own** pack `PA` — URL id and body id both `PA`, so every pack-level guard passes — with `assets[0].asset_pack_id` set to the victim's pack `PB`. Response 200; the attacker's pack reads back empty, the negative control showing the row did not go where the attacker was authorized to write; the victim's pack and their `?owner=` catalogue now contain the attacker's asset. The attacker controls the whole new record, including `model`, `contents`, `script` and `actions`, and the API can delete only the entire pack, not an individual asset.
- The write is **additive only**, and this follows from the code. Touching an existing asset means naming its id, and then both guards do fire: one joins the asset to its pack and rejects a foreign `eth_address`, the other rejects a row whose pack differs from the URL's. Deletion runs through `deleteForAssetPackByIds(id, …)`, scoped `WHERE asset_pack_id = <URL pack>`. Existing assets could not be modified, replaced or deleted, and pack ownership and metadata were untouched.
- Preconditions differ by target. Reaching a **chosen user** also requires that user's asset pack UUID, which the API does not expose — the reporter controlled both identities and so knew both ids. Reaching the **default packs** required nothing: `GET /v1/assetPacks?owner=default` publicly enumerates the 13 official packs owned by `DEFAULT_ETH_ADDRESS`. Either way the attacker needs only a self-registered identity, with no privileged role, LAND or funds. The reporter identified that default-catalogue path and deliberately did not execute it against production, reporting reachability from the code and the public enumeration instead; it was assessed as though carried out, and declining to run it did not count against the report.
- Three further defects on the same handler surfaced while fixing this and are closed by the same change: a soft-deleted pack could be claimed by any caller, a body-supplied `created_at` could switch off the asset-count limit, and two schemas declared `items` without `type: 'array'`, leaving them inert for non-array values.

## Severity

Websites & Applications - Medium.

Reported as Critical under "taking state-modifying authenticated actions on behalf of other users without any interaction by that user", and downgraded on assessment. The unauthorized cross-user write is not disputed, nor that the default asset pack ids are publicly listed and that writes into them required no preconditions. The rating rests on three bounds. First, the write is additive only: existing assets cannot be modified, replaced or deleted and pack ownership and metadata are unaffected, so no content that already exists can be altered or damaged. Second, the affected surface is a long-deprecated feature with effectively no users — these records are not consumed by current creator tooling, and the only editor that reads them is the legacy SDK6 scene editor, which is unreachable from the current Builder UI and cannot be entered by a new user at all, since that requires already owning an SDK6 scene or re-uploading one from the scene pool. That path was wound down publicly over more than two years: the [SDK6 sunset strategy](https://forum.decentraland.org/t/sdk6-sunset-strategy/19560) in late 2023, the [2024 manifesto](https://decentraland.org/blog/announcements/decentraland-2024-manifesto-forging-foundations-for-the-future) committing only to maintenance of the legacy Web Client through 2024, and its replacement shipping with [Decentraland 2.0](https://decentraland.org/blog/announcements/decentraland-2-0-is-live). Usage confirms the outcome — zero deployments through the legacy editor in the last 30 days, fewer than a dozen in the preceding 60 — which is why the default-catalogue path does not lift the rating whether executed or not: anything written there reaches a closed and, by these metrics, inactive population. Third, targeting a specific user requires that user's asset pack identifier, which is not exposed. This is not a claim of zero exposure, only that the impact is bounded by those three factors.

## Solution

[Bind nested asset writes to the authorized parent, and close the sibling defects on the same handler](https://github.com/decentraland/builder-server/commit/64759920aed4b3ef0c385519ec6a66ffc32f9d84) in `builder-server`:

- **Force the parent id (root cause).** `upsertAssetPack` drops any client-supplied `asset_pack_id` while reading the body and re-supplies it from the already-authorized URL id on write: `new Asset({ ...asset, asset_pack_id: id }).upsert()`. In between the assets are typed `Omit<AssetAttributes, 'asset_pack_id'>`, so the compiler rather than a runtime comparison enforces that the value can only come from `id`. This mirrors the treatment the pack's own `eth_address` already had, and is the fix the reporter suggested.
- **Pack takeover after deletion.** The ownership check moved off `Ownable.canUpsert`, which grants when `Model.count({ id }) === 0`. `AssetPack.count` is overridden to add `is_deleted: false`, so a soft-deleted pack counted as zero rows and any caller was authorized for its id. The handler now reads with `AssetPack.findOne(id)`, which does see soft-deleted rows, and rejects when `existingAssetPack.eth_address !== eth_address`.
- **Forged creation dates.** `created_at` and `updated_at` were persisted from the body, and the asset-count limit is gated on `isAfterLimitSplitDate(currentAssetPack.created_at)` — so a caller could backdate a pack past `getLimitSplitDate()` and switch `MAX_ASSETS_COUNT` off. Both are now stripped from the body and derived through `buildModelDates(existingAssetPack?.created_at)`, preserving the original creation date and always stamping `updated_at`. The `eth_address !== DEFAULT_ETH_ADDRESS` exemption was dropped from the limit check, as the date gate already covers the legacy official packs.
- **Schemas that did not constrain.** `assetPackSchema.assets` (`src/AssetPack/AssetPack.types.ts`) and `assetSchema.tags` declared `items` without `type: 'array'`, and JSON Schema applies `items` only to arrays, so a non-array value skipped per-item validation entirely. Both now declare `type: 'array'`. Handler failures also carried no HTTP status, and the asset-count limits were bare `Error`s surfacing as 500s; invalid schema, id mismatch and over-limit are now `badRequest`, and the ownership rejection `unauthorized`.
- **Tests.** A new `test/integration/AssetPack.spec.ts` drives the real Express app over HTTP with genuine auth chains, one case per defect: an asset naming a different pack lands under the URL's pack; an asset owned by another address is rejected with nothing written; a body-supplied creation date is replaced by a server-generated one; a non-owner is rejected whether the pack exists or is soft-deleted; non-array `assets` is rejected by the schema; and an over-limit write with a backdated body upserts neither pack nor asset. `src/AssetPack/AssetPack.router.spec.ts` covers the same invariants at unit level. Both jest configs now pick up `test/**` and raise the timeout to 30s, since these suites boot the app and verify real ECDSA signatures, and the attacker-perspective suite from the previous incident moved from `src/security.spec.ts` to `test/integration/Collection.spec.ts` alongside them. `src/Project/Project.router.spec.ts` moved to persistent mocks, as `clearAllMocks` leaves unconsumed queued implementations for the next test to pick up.
- **Structural guard extended, and its limits recorded.** `src/routeAuthorization.spec.ts` — added for the [2026-07-23](2026-07-23-2.md) publish-authorization incident — now also parses the asset-pack and asset routers, recognises `withAssetPackAuthorization`, and lists `PUT /assetPacks/:id` as handler-authorized. Its docblock now states what it cannot do: it inspects only a route's middleware chain, and says nothing about what a handler does with the request body once the route itself is authorized, such as whether a nested child row is bound to the parent named in the URL.

That last point is the transferable lesson: the previous incident's guard answers "is this route authorized?", and here the answer was correctly yes — the unchecked surface was the body. Authorizing an endpoint says nothing about which rows its payload may reach, so nested writes should derive foreign keys from the authorized parent rather than accept them from the client, and that invariant sits better in the type system than in a route-shape test. The `existsAnyWith…` helpers are worth auditing wherever else they appear: keyed on the child id, they never fire for a child that does not yet exist.
