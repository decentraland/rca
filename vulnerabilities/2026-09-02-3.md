# September 2, 2026 - A stored javascript: forum link in Builder ran in a curator's session

|                          |                   |
| -----------------------: | :---------------- |
|             **Reported** | August-31-2026    |
|           **Mitigation** | September-02-2026 |
|   **Solution Completed** | September-02-2026 |

## Description

- A Builder collection carries a `forum_link`, the URL of its governance forum thread. It is meant
  to be minted server-side by the forum flow (`ForumService` → `${FORUM_URL}/t/{slug}/{id}`); a
  creator never authors it. The curation page renders it as a "Link" control that a committee member
  clicks to open the thread, through `window.open(collection.forumLink, '_blank')`.
- The collection write endpoint did not treat it that way. `PUT /v1/collections/:id` deserialized
  the whole `collection` object and persisted it through a generic `upsert`. `toDBCollection`
  (`builder-server/src/Collection/utils.ts`) stripped only `urn`, `lock`, `created_at` and
  `updated_at`; every other field — including server-owned ones — was written verbatim. This is a
  mass-assignment defect: the endpoint trusted the client for fields the client does not own.
- Nothing constrained the value. The request schema (`Collection.schema.ts`) declared `forum_link`
  as a free string with no scheme or length check, and nothing downstream validated it. An ordinary
  creator, authorized for their own collection and correctly signed, could therefore store an
  arbitrary `javascript:` string in `forum_link` — the report demonstrated this by replaying the
  endpoint's own `GET` response back as the `PUT` body with the field swapped.
- The stored value reached the `window.open` sink unchanged. When a curation committee member opened
  the curation page and clicked the collection's "Link" control (`CurationPage/CollectionRow`), the
  `javascript:` payload executed in the Builder origin with access to the committee member's
  `single-sign-on-*` localStorage — their active 31-day API signing identity. The victim is
  necessarily a committee member, because the vulnerable row is rendered on the committee curation
  page.
- The realized impact was theft of that identity. With it, an attacker could construct valid Builder
  API auth chains as the committee wallet until the delegation expired, and routes that derive the
  caller from the chain — notably `PATCH /v1/collections/:id/curation`, which lets committee
  identities assign reviews and set curation status to `APPROVED`/`REJECTED` — would treat those
  requests as the committee member's. The report signed and decoded that endpoint locally but
  deliberately stopped before the committee lookup, handler, or any database mutation, and sent no
  forged request to production.
- Nothing on-chain was reachable. The ephemeral signing identity cannot sign blockchain
  transactions, so no funds, MANA, NFTs, minting, or on-chain ownership were exposed; the impact was
  confined to off-chain Builder state and the committee member's session. Exploitation also required
  a committee member to click the Link control — user interaction against a small privileged group,
  not a zero-click or broad-audience path.
- The write defect was not limited to `forum_link`. `forum_id` and `reviewed_at` were equally
  client-writable through the same path, and the third-party collection path had no guard against a
  client setting `is_published`/`is_approved` (only the Decentraland path rejected those). The item
  write endpoints, while already stripping server-managed fields, left several free-string fields
  (`thumbnail`, `video`, `utility`, `price`, `beneficiary`) unvalidated for format.

### Root cause

The collection write endpoint drew no boundary between fields a creator authors and fields the
server owns: it persisted the whole client object, so server-managed identity — `forum_link`,
`forum_id`, `reviewed_at`, and on the third-party path `is_published`/`is_approved` — was writable by
any authorized creator. Compounding it, `forum_link` was never constrained to a safe URL scheme at
admission, and the value flowed unchanged into a `window.open` sink on a privileged page, so a
mass-assignment write became script execution in a curator's session.

## Severity

Websites & Applications - High.

This matched the program's "theft of an active user authentication credential" impact: the executed
payload could read the committee member's stored 31-day signing identity. Exploitation needed only an
ordinary creator wallet and the normal save path, plus a committee member clicking the trusted Link
control during routine curation. Kept below Critical because the impact is bounded: it is confined to
off-chain Builder state and one privileged session; the stolen identity cannot sign blockchain
transactions, so no funds, MANA, NFTs, minting, or on-chain ownership are reachable; execution
requires a committee member to click the control rather than firing on its own; and a legitimate
committee member's own account and assets are otherwise unaffected.

## Solution

The fix draws the missing boundary on the server — the write endpoint now ignores every
server-managed field regardless of what the client sends — and validates `forum_link` as an https
URL at admission, with the client hardened independently so an unsafe stored value can never reach a
sink. The two layers are defense-in-depth: either alone stops the reported chain. The report was
received on August 31, 2026; both changes shipped and were deployed to production on September 2,
the server change being the authoritative mitigation and the client change closing the exploit path.

[Ignore server-managed collection fields and validate write input at the request boundary](https://github.com/decentraland/builder-server/commit/72b335698540266a8e63925a6118cdde14cb19f1)
in `builder-server`:

- **Strip server-managed fields (root cause).** `toDBCollection` is the single input boundary for
  both the Decentraland and third-party paths; it now drops `forum_link`, `forum_id`, `reviewed_at`,
  `is_published` and `is_approved` from the client object before the upsert, alongside the existing
  `urn`/`lock`/`created_at`/`updated_at`, while `eth_address`/`salt`/`contract_address` stay
  explicitly recomputed. On insert these columns take their DB defaults; on update, being absent from
  the SET, the existing server value is preserved, and the forum and curation flows keep setting them
  through their own `Collection.update` calls. One change closes `forum_link`/`forum_id`/
  `reviewed_at` on both paths and the third-party `is_published`/`is_approved` gap.
- **Constrain `forum_link` at admission.** The schema now requires an https URL (a new
  `matchers.httpsUrl` = `^https:\/\/`, plus `maxLength: 512`), so a `javascript:`/`data:` value is
  rejected with a 400 before the handler runs; the scheme is validated rather than the host, since
  `FORUM_URL` differs across environments. `reviewed_at` was removed from the schema's `required` set
  so the current client, which no longer sends it, still validates.
- **Validate the item free-string fields.** `thumbnail`/`video`/`utility` reject colon-bearing
  (scheme-prefixed) values, `beneficiary` must be an eth address, and `price` must be a numeric
  string — the item write endpoints hardened in the same pass rather than left for a follow-up.
- **Make schema constraints enforced.** The shared schema-validation middleware now returns on an
  invalid body (`return next(error)`), so `pattern`/`maxLength` constraints stop a request at the
  boundary instead of being advisory.

[Add safe external-link helpers and stop the client trusting server-managed fields](https://github.com/decentraland/builder/commit/87a8d28bce1ea037b3041823d3367caa78c8f8c1)
in `builder`:

- **Centralize safe external links.** `getSafeExternalUrl` (`src/lib/url.ts`) returns a URL only when
  it parses, uses the `https:` protocol and carries no embedded credentials, otherwise `undefined`;
  `openExternal` opens only such a URL with `noopener,noreferrer`, and a shared `<ExternalLink>`
  component renders an `https`-only `<a>` that is always `target="_blank" rel="noopener noreferrer"`
  and inert when the URL is unsafe.
- **Sanitize on read, stop echoing on write.** `forum_link` is coerced to `undefined` when unsafe at
  the redux boundary (`fromRemoteCollection`), so every downstream consumer sees nothing to open, and
  the client no longer echoes `forum_link` or `reviewed_at` back in the `PUT` payload
  (`toRemoteCollection`).
- **Migrate the forum-link sinks.** The reported curation-page control (`CurationPage/CollectionRow`)
  plus `PublishThirdPartyCollectionModal`, `CollectionDetailPage`, the third-party
  `CollectionContextMenu`, `CongratulationsStep` and `RejectionModal` now route through these
  helpers.

Curations were audited and need no change: their write paths build the update from an explicit
`status`/`assignee` whitelist, never spread the request body, and set `additionalProperties: false`.
The forum-post polling flow was left as is, since that endpoint already mints `forum_link`
server-side and the client never authors the link string there.

Regression coverage now includes `toDBCollection` omitting each server-managed field even when
present on the input; the `httpsUrl` matcher accepting https and rejecting `http:`/`data:`/
`javascript:`/bare strings; item fields rejecting colon-bearing, non-address and non-numeric values;
a collection `PUT` that supplies server-managed fields leaving the persisted row unchanged; a
non-https `forum_link` returning 400; and on the client, `getSafeExternalUrl` rejecting non-https and
credential-bearing URLs including case-obfuscated `javascript:` variants, `<ExternalLink>` always
emitting `rel="noopener noreferrer"` and going inert on an unsafe URL, and `fromRemoteCollection`
coercing an unsafe `forum_link` to `undefined`.
