# August 11, 2026 - Invalid scene base lets a Genesis publisher overwrite another publisher's place record

|                          |                |
| -----------------------: | :------------- |
| **Reported on Immunefi** | August-03-2026 |
|           **Mitigation** | August-05-2026 |
|   **Solution Completed** | August-11-2026 |

## Description

- A Genesis City scene deployment carries three related descriptions of its location: the signed entity `pointers`, `metadata.scene.parcels`, and `metadata.scene.base`. The intended invariant is that pointers and parcels are the same unique canonical set and that the base belongs to that set.
- That invariant was split across validation layers. ADR-51 selected `Scene.validate`, whose nested scene property embedded the structural `SceneParcels.schema` but did not execute the custom `SceneParcels.validate` check that enforced `parcels.includes(base)`. Catalyst's production scene access validator then correctly authorized only the signed pointers against LAND ownership and never read the base, relying on stateless validation to have established a coherent scene identity.
- An ordinary publisher authorized for parcel `A` could consequently submit `pointers: [A]` and `scene.parcels: [A]`, but declare an unrelated victim parcel `V` as `scene.base`. The signature, entity validation, and both historical LAND authorization checks passed because the attacker legitimately controlled `A`; no authority over `V` was required.
- Places exposed a second, independent trust-boundary error. Ingestion selected the attacker's existing place through the authorized pointer `A`, but reconstructed the update with `base_position = V`. `PlaceModel.updatePlace` excluded the immutable Places UUID and selected the SQL update target again through the incoming base-position mapping. The second lookup could therefore target the victim's row instead of the row originally selected from `A`.
- The result was a cross-tenant catalog overwrite: the victim row retained its stable Places UUID, and therefore its existing favorites and links, while its visible title, image, creator, and positions were replaced with attacker-selected scene metadata. The Profile Places/Favourites UI then rendered that content to viewers without any victim interaction.
- The attack did not modify the victim's Catalyst entity, LAND, or in-world scene. It corrupted the derived Places catalog record. A victim redeployment could recover the record, although the previously inconsistent rows could require more than one ingestion cycle to converge.
- This was distinct from the [June Worlds parcel-restricted deployment issue](2026-06-08.md). That incident involved `pointers` differing from `scene.parcels`; here those sets could already match and the unchecked `scene.base` was the conflicting identity. Worlds Content Server was not the submitted Genesis exploit route, but it consumed the same scene identity fields and therefore received the same invariant and downstream identity hardening.

### Root cause

The system treated three mutable fields as interchangeable scene identity without validating their relationship once at the boundary or carrying one immutable identity through every subsequent write. A custom semantic invariant in `SceneParcels.validate` was not composed into the parent scene validation, while Places discarded the row identity it had safely resolved and performed a second lookup using untrusted metadata.

## Severity

Websites & Applications - Medium.

This matched “defacing the sites, totally or partially, resulting in unauthorized visual changes of the site which could impact multiple users.” Exploitation required only ordinary publishing authority over one indexed Genesis parcel and an existing victim place mapping. The overwrite reached profile and favorites viewers and preserved the victim UUID's existing favorite relationship, but did not execute code, alter on-chain ownership, change LAND or Catalyst content, or permanently prevent owner recovery.

## Solution

The fix establishes a canonical scene identity at admission and preserves immutable identities across service boundaries and database writes.

### Schemas, Content Validator, and Catalyst

- [`@dcl/schemas` moved base membership into the exported JSON schema](https://github.com/decentraland/schemas/pull/437), so parent validators cannot accidentally omit the semantic check: the declared base must occur in `scene.parcels`, coordinates must be canonical, and parcel and entity-pointer arrays must be unique.
- [`@dcl/content-validator` now runs the complete `SceneParcels` validation](https://github.com/decentraland/core-libs/pull/60), including base membership, and verifies that entity pointers and metadata parcels are the same unique canonical set regardless of order. This was released as `@dcl/content-validator@8.0.0`.
- [Catalyst first added the invariant directly at its production content-validator adapter](https://github.com/decentraland/catalyst/pull/1956), before the access validator can authorize malformed metadata. It rejects invalid new deployments, replays, and backfills even when the pointer authorization itself succeeds. [Catalyst then upgraded to `@dcl/content-validator@8.0.0`](https://github.com/decentraland/catalyst/pull/1957) and removed the now-redundant local wrapper, retaining an adapter-level regression test so the production wiring cannot silently omit the upstream check again.

### Places

- [Places validates pointers, parcels, and base before any database mutation](https://github.com/decentraland/places/pull/856). After overlap resolution it updates the exact immutable Places UUID that was selected, so incoming base metadata cannot retarget the SQL write. A single logical replacement preserves that UUID — and therefore favorites, moderation, ratings, categories, and existing links — while replacing the deployment revision.
- Places now persists the content entity hash as `deployment_id`, uses that producer-owned immutable revision in World deployment and undeployment processing, and applies related place, position, category, rating, and audit mutations transactionally. Stale-event guards and per-world serialization prevent older revisions from winning because SQS messages arrive concurrently or out of order; a guarded base fallback remains only for legacy World rows without a deployment ID.
- A follow-up [added durable undeployment and per-position watermarks](https://github.com/decentraland/places/pull/857). This prevents delayed or redelivered World deployment messages from resurrecting retired scenes after the row that would have demonstrated the conflict is gone. This follow-up was not needed to reproduce the submitted Genesis overwrite, but closes the ordering cases uncovered while making the cross-service identity model durable.

### Worlds Content Server

- [Worlds Content Server independently enforces the same base/pointers/parcels invariant](https://github.com/decentraland/worlds-content-server/pull/521), preserves the validated declared base in multi-scene operations, stops implicitly selecting the first scene where a world contains several, and publishes immutable entity identity plus validated bases in undeployment events.
- For the durable Places ordering fix, [`@dcl/schemas` added optional scene parcel footprints to undeployment events](https://github.com/decentraland/schemas/pull/438), and [Worlds Content Server publishes the canonical footprint when it fits the SNS budget](https://github.com/decentraland/worlds-content-server/pull/526). It retains entity ID and base when a large footprint is omitted, allowing Places to fetch and verify the immutable entity as a fallback rather than dropping the event or splitting it into multiple messages.

Regression coverage now includes invalid bases, canonical and reordered parcel sets, the original cross-row Places update, immutable deployment identity, concurrent and stale deployments, undeployment-before-deployment delivery, redelivery after removal, changed bases, multi-parcel overlaps, large omitted footprints, and legacy fallback behavior.
