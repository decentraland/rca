# August 25, 2026 - Signed-fetch metadata keys fell outside the signature, letting a scene act as the visiting user

|                          |                |
| -----------------------: | :------------- |
|             **Reported** | August-15-2026 |
|           **Mitigation** | August-20-2026 |
|   **Solution Completed** | August-25-2026 |

## Description

- A signed-fetch request is authenticated over the string `method:path:timestamp:metadata`. Both the signer (`decentraland-crypto-fetch`) and the verifier (`@dcl/crypto-middleware`) lowercased that whole string before hashing, so the casing of the metadata was not part of what was signed: `{"signer":"decentraland-kernel-scene"}` and `{"Signer":"decentraland-kernel-scene"}` produced the same bytes and shared one valid signature.
- Explorers stamp requests they sign on a scene's behalf with `signer: decentraland-kernel-scene`, and first-party services reject that marker so a scene cannot reuse the visiting player's identity. [The August 11 fix](2026-08-11.md) made the comparison of that value canonical, but every consumer still looked the property up by its exact name. Renaming the property to `Signer` made `parsed.signer` read as `undefined`, the scene check did not fire, the untouched signature verified, and the service resolved the auth chain as the visitor's wallet.
- The demonstrated target was Rewards. Its owner-only `POST /api/campaigns/:campaign_id/claim_funds` transfers the campaign wallet's balance to an address chosen in the body. A scene the victim walked into could ask the explorer for signed headers, respell the key, and drain a campaign the victim owned, with no prompt or click. Places exposed a smaller version of the same gap on an administrator-only toggle.
- Rewards and Places have no auth code of their own: they verify through `decentraland-gatsby`, which read only the exact lowercase `signer` key and fell through to "signed directly by the user" when it was absent.

### Root cause

The signature and the consumers disagreed about what the metadata was. The library folded the metadata before signing, so a property's spelling was outside the signature, while every consumer read property names exactly as delivered. Any check keyed on an exact property name could be skipped by respelling that name, and the signature stayed valid because the bytes it covered did not change.

## Severity

Websites & Applications - Critical.

This matched "direct theft of funds" and "taking state-modifying authenticated actions on behalf of other users without any interaction by that user". Exploitation needed only that the victim's explorer load an attacker's scene while the victim owned a campaign.

## Solution

The signed payload now covers the metadata bytes as sent, and the guarded fields are refused rather than folded when they arrive in a non-canonical spelling.

- [`@dcl/crypto-middleware` 6.0.0](https://github.com/decentraland/core-libs/pull/68) (August 18) builds the payload from the lowercased method, path and timestamp joined with the metadata verbatim, in both the signer and the verifier. A respelled key now changes the signed bytes and fails verification.
- [6.1.0](https://github.com/decentraland/core-libs/pull/70) adds `rejectIfSigner` and `requireSigner`, which reject a non-canonical `signer` instead of comparing it, so services stop writing the check by hand. [6.2.0](https://github.com/decentraland/core-libs/pull/72) lets comms and scene traffic from explorers that still sign the old payload be accepted while the declared keys are refused when folded, so clients and services could ship in any order.
- [6.3.0](https://github.com/decentraland/core-libs/pull/74) (August 25) closes the last gap: the predicates treated a folded key as absent, and now refuse it.
- [`decentraland-gatsby` 9.0.0](https://github.com/decentraland/decentraland-gatsby/pull/1329) (August 20) takes the new payload in its signer and verifier and refuses a respelled or non-canonical signer; [9.0.1](https://github.com/decentraland/decentraland-gatsby/pull/1330) (August 25) takes 6.3.0. Rewards, [Places](https://github.com/decentraland/places/pull/867), [Events](https://github.com/decentraland/events/pull/1012), [Governance](https://github.com/decentraland/governance/pull/1962) and the other consumers were upgraded between August 21 and August 26.
- Services on the middleware directly were moved to 6.x on August 19 and 20 and to 6.3.0 on August 25, among them [builder-server](https://github.com/decentraland/builder-server/pull/809), [worlds-content-server](https://github.com/decentraland/worlds-content-server/pull/537), [marketplace-server](https://github.com/decentraland/marketplace-server/pull/401), [signatures-server](https://github.com/decentraland/signatures-server/pull/490), [comms-gatekeeper](https://github.com/decentraland/comms-gatekeeper/pull/291), [social-service-ea](https://github.com/decentraland/social-service-ea/pull/493), [credits-server](https://github.com/decentraland/credits-server/pull/597) and [auth-server](https://github.com/decentraland/auth-server/pull/144).
