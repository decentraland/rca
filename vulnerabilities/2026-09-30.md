# September 30, 2026 - Client-controlled Builder forum posts let a collection creator publish content under Decentraland's forum account

|                          |                   |
| -----------------------: | :---------------- |
| **Reported on Immunefi** | September-27-2026  |
|           **Mitigation** | September-30-2026  |
|   **Solution Completed** | September-30-2026  |

## Description

- Builder mints a governance forum thread for a collection through `POST /v1/collections/:id/post`.
  The thread is published to the Decentraland Discourse forum with the platform's own API
  credentials (`FORUM_API_KEY` / `FORUM_API_USERNAME`), so every post the endpoint creates is
  authored by the trusted Decentraland forum account and read by the community and the curation
  committee as an official "collection ready for review" thread.
- For a standard (Decentraland) collection the endpoint trusted the client for the post's content.
  It read `forumPost` from the request, validated it only against a permissive `forumPostSchema`
  (`title` and `raw` as free strings, no length or content constraint), and passed the object
  straight to `createPost(forumPost)`. That client object was sent on to `${FORUM_URL}/posts.json`
  almost unchanged — `createPost` only stripped emojis from the title and forced the `category`,
  while the `raw` body, `topic_id` and `archetype` were forwarded as received. The server composed no
  part of the post. Because `topic_id` was forwarded, this endpoint too could target an existing
  thread, not only create a new one.
- Authorization for the route is `isOwnedOrManagedBy`, so any wallet that owns or manages a
  collection — an ordinary creator — could reach it, correctly signed. The standard path also ran no
  published-collection check, so a throwaway draft collection was enough to obtain the post.
- The result was that a creator could publish an arbitrary thread — any title, any body, any links —
  to the Decentraland forum under the platform's forum identity. Because readers trust that account,
  the attacker-authored content reads as an official Decentraland/forum-staff message: a fake review
  verdict, a fake announcement, or a phishing link inside a thread framed as governance.
- The curation reply path had the same shape for a smaller set of callers. The committee-only
  `POST` new-assignee endpoint took `forumPost` from the client and called
  `createAssigneeEventPost(forumPost)` using the client's `topic_id`, so a committee member could
  post a reply — again under the platform account — to any Discourse topic, not just the collection's
  thread.
- Author attribution was part of that client-controlled content, not a separate server concern.
  Before the fix the standard-collection title — including any "created by" name — was composed by
  the client, so a creator could already frame a thread as authored by anyone. This matters for the
  fix: when it moves title-building to the server, the title reads `Collection '…' created by {name}
  is ready for review!` with `{name}` resolved from the owner's profile, and a Decentraland profile
  name is only unique when it is **claimed** (owned as an NFT name) — an unclaimed name is free text
  anyone can set. Attributing authorship to an unclaimed name would reintroduce the same
  impersonation server-side, which is why the fix uses claimed names only (see Solution).
- The Discourse client also treated a failed forum response as success. It inspected only
  `result.errors` and never `response.ok`, so a non-2xx or non-JSON reply from the forum could be
  read as a created post and a malformed `forum_link` persisted to the collection.

### Root cause

The forum-posting endpoints drew no boundary between what a creator may author and what the platform
account vouches for. The post's content, its author name, and its target topic were all taken from
the client and published under Decentraland's trusted Discourse identity, so an ordinary creator could
put arbitrary words in the platform's mouth. Separately, the client's success detection ignored the
HTTP status, letting a failed post look like a successful one.

## Severity

Websites & Applications - High.

The impact is impersonation of an official Decentraland communication channel: attacker-authored
content published under the platform's forum account and presented to the community and the curation
committee as official. Exploitation needs only an ordinary creator wallet and the normal save path,
with no wallet interaction from any victim. It is held below Critical because the attacker cannot act
as an arbitrary victim user or touch another user's account, funds, MANA, NFTs, or any on-chain
state: the post is published under a single service identity within the collection-review flow, and
the effect is confined to off-chain forum content. The curation-reply variant is further bounded to
committee members. The client's success-detection gap is a lower-severity weakness hardened in the
same pass.

## Solution

The fix moves authorship to the server: the endpoints now build the forum content themselves and
ignore whatever the client sends, resolve the target topic from stored state rather than the request,
attribute authorship only to claimed names, sanitize the creator-controlled text that legitimately
appears in a post, and treat a failed forum response as a failure. It shipped in
[builder-server#812](https://github.com/decentraland/builder-server/pull/812) and was deployed to
production on September 30, 2026.

- **Server builds the post; client input is ignored (root cause).** The handler no longer reads a
  client `forumPost`. It resolves the collection, builds the title and body from server state through
  `ForumService`, and passes only that to the Discourse client, so a creator can no longer choose the
  title, body, links, or archetype of a post published under the platform account. The standard path
  also now rejects an unpublished collection with a 409 before any post is attempted (third-party
  collections skip that check, as before), and when a post already exists the endpoint returns 409
  with the existing `forum_link` so the client can recover instead of retrying.
- **Curation replies resolve their own topic.** The new-assignee endpoint no longer trusts the
  client's `topic_id`. It loads the collection, derives the topic from the collection's own forum
  post, validates the reply body (non-empty, length-bounded), and posts only to that topic, so a
  committee member can no longer target an arbitrary Discourse thread.
- **Authorship uses claimed names only.** `getProfileName` now returns a name only when the profile's
  `hasClaimedName` is true; an unclaimed or missing name falls back to the shortened owner address, so
  a free-text profile name can no longer be used to attribute a review thread to someone else.
- **Creator-controlled text in the body is neutralized.** The collection-name heading and the item
  names/descriptions in the post body are escaped so they cannot inject Discourse mentions, links, or
  markdown; the title keeps only its existing emoji strip. A duplicate collection title is retried
  once server-side with the shortened contract address appended instead of surfacing a Discourse error
  to the client.
- **The Discourse client trusts the HTTP status.** `createPost`, `updatePost`,
  `createAssigneeEventPost` and `getPost` now reject a non-2xx or non-JSON response instead of
  treating it as success, so a failed forum call can no longer persist a malformed `forum_link`, and
  the forum and profile fetches carry a 10-second timeout.

Regression coverage was added for the endpoint ignoring client-supplied `title`/`raw`/`topic_id`/
`archetype`, the 409 on an unpublished collection, the curation reply resolving its own topic and
rejecting oversized or empty bodies, claimed-versus-unclaimed name resolution, the creator-text
sanitization, the duplicate-title retry, and the client's non-2xx and non-JSON handling.
