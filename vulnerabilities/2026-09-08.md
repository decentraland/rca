# September 8, 2026 - A scene fetch() followed a cross-scheme redirect to file:// and returned the local response

|                          |                   |
| -----------------------: | :---------------- |
|             **Reported** | September-07-2026 |
|           **Mitigation** | September-08-2026 |
|   **Solution Completed** | September-08-2026 |

## Description

- The desktop Unity client exposes a `fetch()` API to every SDK7 scene
  (`SimpleFetchApiImplementation.FetchAsync`). Scene code is untrusted attacker input: a scene the
  victim walks into runs automatically, with no download, prompt, click, or wallet approval. The API
  is meant to let a scene talk to https web services only; outside Local Scene Development it is
  https-only by policy.
- The scheme check was applied to the wrong URL. `FetchAsync` verified that the **initial** URL
  began with `https://`, then handed the request to `UnityWebRequest`, which follows redirects
  automatically. The response builder (`SimpleFetchAdHoc.GenerateResponseOp`) copied the **final**
  URL and body verbatim, and `SimpleFetchApiWrapper` returned both to the scene. Nothing re-checked
  the scheme after the redirects, so a request that started on `https://` could complete on a
  different scheme and the client returned that response.
- The scene's own `redirect` argument gave no protection either. `FetchAsync` accepted a `redirect`
  parameter but never applied it: a scene passing `redirect: "error"` still received the redirected
  body, and the response was reported back as `redirected` rather than refused.
- Chained together this turned the client into a local-file reader. A direct
  `file:///C:/Windows/Logs/DISM/dism.log` request was rejected by the initial check, but the same
  target behind an attacker-controlled `https://` URL that 302-redirected to that `file://` path
  succeeded, returning the local file contents with a final scheme of `file` and status `0`. The
  demonstrated Windows chain read a fixed system log to recover the OS profile (user) name, then a
  second attacker-controlled https redirect pointed at that user's persisted client data file
  (`%AppData%/LocalLow/Decentraland/Explorer/userdata_0.json`), whose `Web3Authentication.Identity`
  entry holds the persisted **ephemeral identity**: the ephemeral private key and its delegation
  auth chain.
- The realized impact was theft of that credential. With the ephemeral key and auth chain, an
  attacker can construct fresh valid Decentraland authentication chains as the victim until the
  delegation expires. The proof of concept was built entirely from synthetic, locally seeded
  credentials and loopback capture endpoints, and validated the recovered chain offline with
  `@dcl/crypto`; it demonstrated the read-and-exfiltrate path without touching production identity
  data or a public realm.
- The impact is bounded. The path was demonstrated on Windows hosts that have a persisted identity
  and a readable fixed log exposing a usable profile path; it does not reach the wallet owner's root
  key or seed, on-chain funds, MANA, NFTs, or minting, since the ephemeral identity cannot sign
  blockchain transactions. The exposure is the off-chain session identity, valid until the ephemeral
  delegation expires.

### Root cause

The https-only policy was enforced against the URL the client was asked to request, not the URL it
actually retrieved. Because `UnityWebRequest` follows redirects transparently, the request that was
checked and the response that was returned could describe different schemes, and every stage after
the initial check trusted the redirect chain: the response builder copied the final URL and body
unchanged, and the scene's `redirect` policy argument was accepted but never applied. A single
https gate at the front of a redirect-following request is not a scheme boundary.

## Severity

Websites & Applications - High.

This matched the program's "theft of an active user authentication credential" impact: the returned
body carried the victim's persisted ephemeral identity, from which fresh valid auth chains can be
minted until expiry. Retrieval needs no interaction beyond the victim entering an attacker's scene.
Kept below Critical because the impact is bounded to the off-chain session identity: the ephemeral
key cannot sign blockchain transactions, so no funds, MANA, NFTs, minting, or on-chain ownership are
reachable; the credential is valid only until the ephemeral delegation expires; and the demonstrated
chain depended on a host-specific readable local path (a Windows fixed log exposing the profile
name) to locate the identity file.

## Solution

[Enforce https on the fetch() final URL after redirects](https://github.com/decentraland/unity-explorer/pull/10023)
in `unity-explorer` (merged September 8):

- **Re-check the scheme after retrieval (root cause).** `FetchAsync` now routes every verb
  (GET/POST/PUT/DELETE/PATCH, including the profiles-intercept path) through a single return point
  and applies the same https policy to the response's **final** URL, not only the initial one. When
  the final URL is not https outside Local Scene Development, the response is replaced with an empty
  `type: "error"` response (`Ok = false`, `Status = 0`, no body, no headers), so a scene can never
  observe the contents of a non-https redirect target. One warning is logged for triage. The Local
  Scene Development exemption is preserved, matching the initial check.
- **Pure, testable guards.** The decision and replacement live in `IsHttps` /
  `ShouldBlockNonHttps` / `EnforceHttpsFinalScheme`. `IsHttps` also replaces the earlier
  `url.ToLower().StartsWith("https://")` with an allocation-free ordinal, case-insensitive compare,
  so the initial check no longer allocates a lowercased copy per request.
- **Regression coverage.** A new EditMode suite (`SimpleFetchApiSchemeGuardShould`) exercises the
  guard without a live `UnityWebRequest`: an https final URL is returned unchanged; a non-https final
  URL (a `file://` or internal `http` redirect target) outside Local Scene Development is dropped to
  an empty error response; and a non-https final URL under Local Scene Development is returned
  unchanged, holding the dev exemption.

The remaining hardening the report suggested - refusing intermediate redirect hops before the final
one, and honoring the scene's requested `redirect` mode rather than always following - is broader
transport-security work tracked separately alongside the client's cleartext-scheme policy, and is
not required to close the reported credential-retrieval path: the final-scheme check already stops a
non-https response body from reaching a scene.
