# September 4, 2026 - A USD-priced listing was shown and charged as if the amount were MANA

|                          |                   |
| -----------------------: | :---------------- |
|             **Reported** | September-04-2026 |
|           **Mitigation** | September-10-2026 |
|   **Solution Completed** | September-11-2026 |

## Description

- The off-chain Marketplace supports listings whose price asset is `USD_PEGGED_MANA`: the signed
  amount is a USD value with 18 decimals, and the contract converts it to MANA from its configured
  oracle feeds at the moment the buyer executes the order. The server accepts and indexes these
  trades correctly, and keeps them tagged.
- The legacy Orders projection dropped the only thing that told them apart. `getTradesOrdersQuery`
  projects the received amount as `price` and selects no asset type, so a MANA-denominated order and
  a USD-denominated one reach the client as the same integer with no currency attached.
- `BuyNftWithCryptoModal` read that integer as MANA. The same value fed the confirmation price, the
  MANA-to-fiat line, the payment selector, the purchase total, the balance check, and
  `requiredAllowanceInWei`. A listing priced at 100 USD was presented as `100 MANA`, the Buy action
  was enabled for a wallet holding exactly 100 MANA, and the spending allowance was requested for
  100 MANA.
- Settlement debited the converted amount. In the fork reproduction, at the conversion input used
  there, that listing debited 1,380.257258111318890522 MANA — 13.8× what the buyer was shown — of
  which 1,345.750826658535918259 reached the attacker-controlled seller after the 2.5% fee. A buyer
  who already held a larger allowance went straight through; a buyer who needed a new one granted
  the usual unlimited approval, which covered it too. The multiple grows as MANA falls below one
  dollar.
- The converted amount was rendered correctly everywhere else — browse cards, collection and
  listing tables, on-sale lists, asset detail page — because those surfaces had already been
  corrected. Reaching the understated figure therefore required sending the buyer a link that opens
  the confirmation step directly, which the application supports as a first-party route.
- The sink was activated rather than introduced: the outer display surfaces were fixed first, then
  USD-pegged trades were made buyable, while both checkout modals stayed byte-identical through all
  of it.

### Root cause

A value that can be denominated in two different currencies travelled through the application as a
bare integer, and the one layer that knew which currency it was — the typed trade — was flattened
away before the client saw it. Correcting the surfaces that *display* the number does not help when
the surface that *authorizes the spend* reads the same untagged value.

## Severity

Websites & Applications - Critical.

It matched "performing malicious interactions with an already-connected wallet such as modifying
transaction arguments or parameters ... stealing funds or assets": the buyer authorizes one amount
and a larger one is debited. Kept at the lower end of the tier because every browsing surface showed
the correct converted price, so reaching the understated figure requires delivering the buyer a
direct link to the confirmation step rather than being something they meet while browsing.

## Solution

Resolve the USD-pegged amount into MANA before anything reads it, in two rounds.

Marketplace 8.33.2 (September 10):

- **Convert before checkout (root cause).**
  [#2705](https://github.com/decentraland/marketplace/pull/2705) resolves the amount into MANA ahead
  of the checkout total, the required allowance, the balance check, the Credits subtraction, the
  native purchase, and the cross-chain source and destination amounts.
- **Convert everywhere else that consumed the same field.**
  [#2706](https://github.com/decentraland/marketplace/pull/2706) covers the asset page and action
  box, the balance-based call to action, post-purchase Credits calculations, and the Transak quote —
  the assumption was spread across independent paths, not confined to one label.

Marketplace 8.34.0 (September 11), after a follow-up finding that a mobile in-app-purchase deep link
still reached a Credits-branded confirmation while executing an ordinary full-price MANA purchase:

- [#2708](https://github.com/decentraland/marketplace/pull/2708) sends the supported mobile
  in-app-purchase entry points to the Shop.
- [#2709](https://github.com/decentraland/marketplace/pull/2709) binds the displayed branding, the
  displayed amount and the executed action to the payment source actually selected, carries the
  Credits selection into deep-link checkout, and normalizes the route variants that bypassed the
  earlier handoff.
