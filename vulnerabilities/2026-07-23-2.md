# July 23, 2026 - Missing third-party manager authorization on the Builder collection publish route

|                          |               |
| -----------------------: | :------------ |
| **Reported on Immunefi** | July-23-2026  |
|           **Mitigation** | July-27-2026  |
|   **Solution Completed** | July-27-2026  |

## Description

- `POST /v1/collections/:id/publish` mounted only `withCors`, `withAuthentication` and `withCollectionExists` (`builder-server/src/Collection/Collection.router.ts`). Unlike its sibling routes `POST /collections/:id/lock` and `DELETE /collections/:id`, it did **not** mount `withCollectionAuthorization` — `withModelAuthorization(Collection, 'id', …)` resolving to `CollectionService.isOwnedOrManagedBy`, which for a third-party collection is `ThirdPartyService.isManager`. Any wallet holding a valid auth chain of its own therefore reached the handler for any existing collection id.
- For a third-party (linked-wearable) collection the handler calls `CollectionService.publishTPCollection`, which validated the *cheque* and nothing else: `getAddressFromSignature` (`src/Collection/utils.ts`) is `ethers.utils.verifyTypedData` over the EIP-712 `ConsumeSlots` payload, and its result was compared to `req.auth.ethAddress`. That only proves the caller signed their own cheque — it says nothing about their relationship to the third party. `ThirdPartyService.isManager` was never called. Authorization was absent at both the route and the service layer.
- With no check in place, an unauthorized request ran the full write block: a `slot_usage_cheques` row carrying the attacker's signature, one `item_curations` row per requested item at `pending`, a `collection_curations` row at `pending`, and a forum topic published for the victim's collection via `ForumService.upsertThirdPartyCollectionForumPost`.
- The persisted state has durable consequences for the victim project. Builder reports remaining capacity as `Number(thirdParty.maxItems) - ItemCuration.countByThirdPartyId(…)` (`ThirdPartyService.getThirdPartyAvailableSlots`), so every forged curation reduces the slot count shown to the paying third party. The pending `ItemCuration` also trips `AlreadyPublishedCollectionError`, so the legitimate manager's own publish attempt is rejected with a 409 for as long as the forged review stays open. And because publication state is what gates public reads, the collection and its unpublished items become readable by unrelated wallets once the forged publication exists.
- Precondition: the collection's UUID, the id of one unpublished item in it, and a self-generated wallet. No victim signature, click, wallet connection, installed application or committee involvement is required. The reporter obtained both ids from `GET /v1/collections/:id/items`, which returned unpublished children of a public collection — a separate root cause, reported separately, and also addressed by this change (see Solution).
- Scope limit: the vulnerability only lets an attacker send **already-existing** items of the victim's collection into review. `publishTPCollection` resolves the request through `Item.findByIds(itemIds)` and then requires `dbItems.every(item => item.collection_id === collectionId)`, so the attacker cannot create items, add items to the collection, edit them, or pull items in from another collection — the item ids must already belong to the collection being published. Item creation and editing go through `PUT /items/:id`, which authorizes inside its handler and was not affected.
- Scope limit: the stored cheque is signed by the attacker rather than a manager, so it cannot be redeemed against the `ThirdPartyRegistry` contract — no on-chain slots are consumed and no funds are at risk. The impact is therefore an unauthorized, durable review submission on another project's behalf: denial of that project's publication flow, Builder-side capacity consumed, disclosure of its unpublished drafts, and a forum post attributed to it. The missing check was confirmed against `builder-api.decentraland.org` with a pre-write probe: the request reached the late `Cannot publish items that belong to different collections` guard, which in the published source runs *after* the slot, item, quantity and signature-recovery checks, so production had accepted a wallet it had just rejected on the manager-only slots route. The full database effect was then reproduced end-to-end against release `5.19.2` (commit `ed5b295`) on real PostgreSQL migrations with only external dependencies (Graph, Catalyst, forum, warehouse, RPC) stubbed.

## Severity

Websites & Applications - High.

An unauthorized wallet takes a state-modifying, authenticated action against another user's collection with no interaction by that user, and the resulting publication state discloses that user's confidential unpublished items. Kept below Critical because the action available is narrow and its damage is not financial: the attacker can only submit the victim's own existing items for review — not create, add, edit or move items — and the attacker-signed cheque is unredeemable on-chain, so no slots are truly spent and no funds are at risk. What remains is durable Builder-side state the victim did not authorize, denial of that project's publication flow while the forged review is open, exposure of its drafts, and a forum post attributed to it.

## Solution

[Authorize the publish path at both layers and scope what unprivileged callers may read](https://github.com/decentraland/builder-server/commit/e4bb74f6fc8f961e33c292f1837e668b8a1e0bf0) in `builder-server`:

- **Route gate (root cause).** Mount `withCollectionAuthorization` on `POST /collections/:id/publish`. It is also mounted on `POST /collections/:id/tos`, which had the same omission and let any wallet file a Terms-of-Service acceptance — email, URN and content hashes — to the warehouse for a collection it does not own.
- **Service gate (defense in depth).** `CollectionService.publishTPCollection` now requires `ThirdPartyService.isManager(dbCollection.third_party_id, signerAddress)` before it reads the slot count or writes anything, throwing `UnauthorizedCollectionEditError`; the router maps that to 401 instead of letting it escape as a 500. Callers reaching the service directly, bypassing the route, are refused too.
- **Read scoping** (this also resolves the separately reported child-disclosure, and removes the id-discovery step this attack depended on). `canSeeCollection` / `canSeeItem` decide whether a caller receives the full record or a redacted one. In collection *listings*, `toPublicCollection` omits `id` along with `salt`, `forum_link`, `forum_id` and `lock`, so an unprivileged caller no longer harvests collection UUIDs; on a single-collection fetch, `toPublicCollectionDetail` keeps the `id` the caller already supplied and strips the same internal fields. `toPublicItem` drops `local_content_hash`. `GET /collections/:id/items` re-queries with `onlyPublished: true` for unprivileged callers — an `Item.findByCollectionId` filter requiring the item's *own* `blockchain_item_id` or its *own* `item_curations` row — so a collection-level curation no longer exposes unrelated drafts, the paginated total reflects published items only, and the id of an *unpublished* item is no longer obtainable, which is the precondition the publish attack needed.
- **Curation authorization.** Approving or rejecting a curation now requires `isCommitteeMember`. Previously any caller who passed `validateAccessToCuration` — including a third-party manager — could set their own curation to `approved`, which triggers `updateCollectionItemsContent` and deploys to the Catalyst, bypassing the curation committee entirely. Setting a curation's `assignee` at insert time now requires committee membership, matching the check that already existed on update. And `CollectionCuration.updateByItemId` — a write — moved from the top of `updateItemCuration` to after the access checks, so an unauthorized caller can no longer touch the victim's collection curation before being rejected.
- **Authorization-comparison correctness.** `Collection/access.isManager` compared `manager.toLowerCase()` against a raw `eth_address`, and `CollectionService.isDCLManagerOfCollection` used strict equality; both now lower-case both sides, and a matching `isMinter` helper was added. Third-party item upserts now honour the collection `lock` through `isLockActive`, matching the behaviour of the DCL path.
- **Async middleware.** `withModelExists`, `withCollectionExists` and `withModelAuthorization` are `async`, but their rejections were never routed to `next` — a failing existence or ownership check left an unhandled rejection and a hung request rather than a 500. All three are now wrapped in a new `guardAsync` helper.
- **Regression guards.** `src/routeAuthorization.spec.ts` parses the collection, item and curation routers and fails if any mutating route has neither an authorization middleware nor an explicit `HANDLER_AUTHORIZED` entry naming the mechanism it authorizes with inside the handler — the structural guard against this class of omission recurring. `src/security.spec.ts` drives the real Express app with an attacker-owned auth chain and asserts that publish, ToS, curation-approval and item-edit attempts are rejected *and* that no cheque, curation, item or warehouse write occurs. `.gitignore` was extended with `.env.*`.
