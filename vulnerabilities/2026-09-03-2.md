# September 3, 2026 - Estate offers were signed against a composition the bidder was never shown

|                          |                   |
| -----------------------: | :---------------- |
|             **Reported** | September-03-2026 |
|           **Mitigation** | September-16-2026 |
|   **Solution Completed** | September-16-2026 |

## Description

- An offer on an Estate carries the Estate's fingerprint, which the contract verifies at settlement
  so the bidder cannot be handed a different composition than the one they bid on. For that to mean
  anything, the fingerprint has to describe what the bidder actually reviewed.
- `BidModal` had both values and used the wrong one. `useFingerprint` returns the fingerprint
  derived from the composition on screen **and** the one read live from the Registry; the component
  discarded the first and passed `contractFingerprint` to `onPlaceBid`, which wrote it into the
  trade as `received[0].extra`. Nothing compared the two.
- The displayed composition can be stale for a whole session, not for a block. `AssetProvider`
  refetches only when it has no asset at all, so once the Estate page has loaded composition A it
  keeps rendering A through the single-page navigation into the offer flow and into the final
  confirmation screen.
- An owner who replaces composition A with composition B after a bidder has loaded the page, and
  before the offer form reads the fingerprint, gets a signature bound to B while the bidder reviews
  and confirms A. The owner can then accept the standing offer without any further action from the
  bidder, take the MANA and deliver B. The reported case showed a 20-parcel Estate, delivered a
  1-parcel one, and debited 1,000 MANA.
- This is a regression rather than an original defect. A check comparing the displayed fingerprint
  against the contract one existed since 2024 and was removed in May 2026, when the signed value was
  switched to the live `contractFingerprint` to stop false mismatches produced by computing the
  fingerprint locally.

### Root cause

Same shape as the Auth cases in a different surface: what the user reviewed and what the user signed
came from two independent reads, and only the second one was authoritative. Removing the comparison
between them left nothing requiring that they describe the same Estate.

## Severity

Websites & Applications - Low.

The binding failure is real and was reproduced, but it cannot be aimed. The owner has to change the
composition inside an interval they cannot observe — nothing tells them a bidder has the page open —
so landing inside it is chance; narrowing it means inducing the visit, which moves the decisive step
outside our application. Repeating the attempt works against the attacker: every composition change
invalidates all offers signed before it, the parcel list is swap-and-pop so putting a parcel back
does not reproduce the previous fingerprint, and between attempts the Estate sits publicly stripped,
so new offers arrive against the reduced composition.

## Solution

[Bind the Estate shown at review to the fingerprint that gets signed](https://github.com/decentraland/marketplace/pull/2716)
(merged September 16, shipped in Marketplace 8.35.2):

- **One pinned read (root cause).** The composition and the fingerprint are read at the same block,
  the page renders that snapshot, and the fingerprint is re-checked against it before the signature
  is requested.
- **Say so when it changed.** A composition warning tells the user when the Estate on screen no
  longer matches the chain, instead of silently signing the newer one.
- Applied to both Estate paths that sign a fingerprint — placing an offer and buying — and to the
  map and detail views that render the composition.
