# September 12, 2026 - Ordinary scene JavaScript reached arbitrary native memory through a stale V8 WasmGC tag check in Godot Explorer

|                          |                   |
| -----------------------: | :---------------- |
| **Reported on Immunefi** | September-12-2026 |
|           **Mitigation** | Pending            |
|   **Solution Completed** | Pending            |

## Description

- Godot Explorer's scene sandbox disables scene WebAssembly by overriding the
  `WebAssembly.Module` and `WebAssembly.Instance` constructors. The static `WebAssembly.instantiate`
  entry point is not overridden and still reaches the real V8 WebAssembly implementation, so the
  guard blocks one way of getting a WASM module running but not the one actually in use.
- The client's pinned `rusty_v8`/`deno_core` version embeds a V8 whose WasmGC tag validation
  (`WasmTagObject::MatchesSignature`) accepts an imported tag whose type is merely a canonical
  *subtype* of the exporting module's tag, instead of requiring exact type equality. A scene can
  ship one WebAssembly module that exports a tag carrying a short struct and a second module that
  imports it as a longer subtype; the consumer then reads/writes fields that don't exist in the
  provider's real memory layout. Upstream V8 fixed this by tightening the check to exact canonical
  equality; the client's pinned version predates that fix.
- Chained into `addrof`/`fakeobj`/arbitrary-read/arbitrary-write primitives, this gives ordinary
  scene JavaScript controlled out-of-bounds read and write, full object-address disclosure, forged
  object references, and chosen-address native memory access — reachable the moment a victim enters
  the scene, with no download, prompt, click, or wallet approval needed.
- The demonstrated proof went further than raw memory access: it located the native function
  objects backing two of the client's own `Deno.core.ops` host operations, overwrote one's backing
  words with the other's (so calling the first op returned the second op's value instead), then
  restored the original bytes. This shows the primitive reaches client-owned control state, not
  just memory the scene already owns as WASM linear memory.
- The exact vulnerable compiled code was confirmed present in the officially released Android build
  (byte-for-byte match against the pinned V8 archive), with the V8 sandbox and pointer compression
  both disabled in that build, and reproduced end-to-end against the full unmodified headless client
  binary, not only an isolated runtime harness.

### Root cause

The sandbox guard blocked the wrong API surface: it disabled the two constructors a scene would use
to *construct* a WebAssembly module directly, but never touched `WebAssembly.instantiate`, which
remained a fully working path into a V8 engine version whose WasmGC tag-import check was too
permissive. Blocking specific constructors instead of removing the capability itself, combined with
carrying a V8 version that predates a known type-safety fix in that exact subsystem, is what let
ordinary scene code cross out of the JS sandbox into native memory.

## Severity

Escape sandbox attack from scenes - High.

This matched "escape sandbox attack from scenes (injection of HTML or code injections in main
thread from deployed scene code)." Exploitation needs only that the victim enter a scene the
attacker controls; native memory read/write and host-op dispatch redirection were demonstrated, but
the proof stopped short of the target being an official bounty-scoped asset, and stopped short of
demonstrating a further escalation beyond the shown redirection primitive.

## Solution

Not yet merged. The required changes are:

- Upgrade `rusty_v8`/`deno_core` to a version whose V8 embeds the WasmGC canonical-subtype fix
  (a patched-control build using `deno_core 0.319.0` / `v8 130.0.1` was confirmed to reject the same
  modules with `LinkError`), subject to compatibility testing against the rest of the JS runtime.
- Fix the scene sandbox guard to actually deny scene WebAssembly: block `WebAssembly.instantiate`
  (not only the `Module`/`Instance` constructors), ideally by removing scene access to a working
  `WebAssembly` global entirely rather than patching individual entry points one at a time.
- Add a regression test asserting scene code cannot get a WebAssembly module running through any
  entry point, not just the two constructors currently checked.
- Consider enabling the V8 sandbox and pointer compression in the shipped build as defense-in-depth
  against this class of bug, if feasible.
