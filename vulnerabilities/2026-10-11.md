# October 11, 2026 - Rental listings were matched to on-chain rentals by signature alone

|                          |                   |
| -----------------------: | :---------------- |
|             **Reported** | October-09-2026   |
|           **Mitigation** | October-11-2026   |
|   **Solution Completed** | October-11-2026   |

## Description

- signatures-server keeps the off-chain copy of rental listings that the marketplace shows. When the rentals subgraph reports a rental, the server finds the listing it belongs to and marks it as executed with the rental's tenant. This happens in two places: the rentals job, which runs every five minutes, and the unauthenticated refresh `PATCH /v1/rentals-listings/:id`.
- Both lookups matched the rental to the listing by signature bytes alone. They never compared the rental's contract address, token id or lessor with the listing's.
- The signature carried by an `AssetRented` event is whatever the caller of `Rentals.acceptOffer` passes. The contract verifies a contract signer through ERC-1271, accepts any ERC-721 address and takes no payment when `pricePerDay` is 0. Every open listing's signature is public through `GET /v1/rentals-listings?status=open`.
- Any wallet could deploy a dummy ERC-721 and an ERC-1271 contract that accepts any bytes, then call `acceptOffer` on the dummy token with a victim's listing signature, `pricePerDay = 0` and `rentalDays = 1`, about 156k gas. The subgraph stored the rental with the victim's signature, and on the next job run, or right away through the refresh, the victim's listing became executed with the attacker's contract as tenant and dropped out of the marketplace's open listings.
- The effect was off-chain and recoverable. The owner signed nothing, no funds moved, and the owner's listing stayed valid on the contract: their nonces were untouched and it could still be accepted through `acceptListing`. The owner could publish a new listing right away, and the attacker could remove it again the same way. Rentals exist only on Ethereum for LAND and Estates, 83 open listings at the time.

### Root cause

The off-chain mirror used a key with fewer dimensions than the on-chain event. A rental is identified on chain by (contract, token id, lessor) and the signature is only a payload of that event, so a rental on one asset could be attached to a listing of a different asset and a different owner that happened to share the signature bytes. The same shape appeared a month earlier in the cancellation path of this service, which dropped the signer dimension of the asset index.

## Severity

Websites & Applications - Medium.

The off-chain copy of another user's listing was changed, with status set to executed and tenant set to the attacker's contract, without any interaction from that user. It was not assessed as Critical because no action requiring the owner's authentication was performed: the attacker's transaction rents the attacker's own token to the attacker's own contract, and the owner's signature only served as a lookup key in the indexer. It was not a signature replay either, since the contract never verifies the owner's signature on that path.

## Solution

[signatures-server 1.10.4](https://github.com/decentraland/signatures-server/pull/492) (October 11) matches an indexer rental to a listing by contract address, token id and lessor as well as signature, in both the rentals job and the listing refresh. A rental on a different asset or by a different lessor no longer touches the listing. The unit test for the refresh covers the extra query variables.
