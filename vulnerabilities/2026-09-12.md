# September 12, 2026 - Production Mobile Hub bundled a whitelisted test key accepted for backoffice administration

|                          |                   |
| -----------------------: | :---------------- |
| **Reported on Immunefi** | September-12-2026 |
|           **Mitigation** | September-16-2026 |
|   **Solution Completed** | September-16-2026 |

## Description

- Mobile Hub's production build ships a fixed Hardhat local-dev private key (`DEV_PRIVATE_KEY`,
  Hardhat account #0) in its client-side JavaScript bundle. The key is defined for local
  development convenience; a `localhost` check gates when the app *uses* it, but the constant
  itself is still imported into code reachable by Vite's production bundler, so it ends up in the
  bundle served from the CDN regardless of where the page is loaded from.
- Mobile BFF's `/backoffice/*` routes apply ADR-44 signed-fetch authentication and check the
  recovered signer address against an `ALLOWED_USERS` list. The address corresponding to that same
  Hardhat key is present in the production allowlist.
- Because the private key is public (it is one of Hardhat's well-known default test accounts, and
  now also directly extractable from the production bundle), anyone can derive it, construct a
  valid ADR-44 auth chain, and sign requests as an allowed backoffice administrator with no
  credentials of their own.
- This was verified with GET requests only: an unsigned request returns 401, a request signed by an
  unrelated freshly generated key returns 403, and a request signed with the key extracted from the
  bundle returns 200 with live backoffice data (feature flags, including who last changed each one).
  The same authorization check gates the write handlers for feature flags, mobile app versions,
  bans, campaigns, tags, Places, and place groups; no state-changing request was sent during
  validation.

### Root cause

A development-only secret was reachable from the production client bundle, and its corresponding
address was never excluded from (or was never removed from) the production admin allowlist. The
`localhost` gate controlled when the helper ran locally, not whether the constant shipped to
production, so the two facts — a public well-known key, and that key's address holding backoffice
privileges — coexisted safely only as long as nobody looked.

## Severity

Websites & Applications - Critical.

This matched "taking state-modifying authenticated actions ... on behalf of other users without any
interaction by that user." Any anonymous visitor to the public production page could derive a
working administrator identity with no interaction from a legitimate user and no additional
access. The write endpoints behind the same check were not exercised during validation, but share
the identical authorization gate as the read endpoints that were confirmed.

## Solution

We removed the exposed address from the production `ALLOWED_USERS` environment variable on Mobile
BFF. The key itself is a public, well-known Hardhat test account and can't be rotated back to
secret, so revoking its production privileges is what actually closes the path: the same request
that previously returned 200 now falls back to the ordinary 403 any other unlisted signer gets.
